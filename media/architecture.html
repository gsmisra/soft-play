Executive Summary

What SoftPlay is, in five sentences a software architect can act on.

  • 1SoftPlay is a VS Code extension that records browser flows with Playwright Codegen, or a manually-built REST request, and turns either into production-style test code using GitHub Copilot's LLM.
  • 2Two automation modes, one pipeline: UI Automation (Playwright, browser-driven) and API Automation (REST Assured / requests, no browser) share the same settings, caching, and LLM plumbing.
  • 3Nothing runs in the cloud except the LLM call itself. Browser recording, code execution, environment checks, and all caching happen as local child processes / in-process memory on the developer's machine — a deliberate fit for bank/enterprise networks with restricted egress.
  • 4The LLM is never bundled or self-hosted. SoftPlay borrows the user's own GitHub Copilot Chat subscription via VS Code's standard vscode.lm API — no API keys stored, no separate billing relationship.
  • 5Caching is intentionally simple: three in-memory, TTL-bound caches (no Redis, no disk database) cut down repeated process spawns and repeated LLM token-counting calls, without ever risking a stale answer for something that matters.
  • 6Every credential is encrypted by default — in both modes, with no setting to turn it off. See "Auto Password Encryption" in Components.
  • 7"Verify & Fix Code" is a real LangChain tool-calling agent — not a hardcoded retry loop. It runs the code itself, reads whatever context it decides it needs, and only stops on a machine-verified pass — see "Verify & Fix Agent" below.
  • 8Code generation now reuses your team's own helpers, not just Copilot's guesses — a local, zero-external-service RAG layer (see "Reusable Components (RAG)") retrieves the right one from .github/rag/ and hands Copilot the exact code and import to call.

How ownership is wired

Composition root

extension.ts

On activation, creates one SettingsStore and one ObjectSpyPanel, registers the sidebar view + four commands (objectSpy.openPanel, .start, .stop, .openSettings), and hands both to context.subscriptions so VS Code disposes them cleanly on deactivate.

Panel owns panels

ObjectSpyPanel

The Control Panel is the orchestrator: its constructor instantiates SettingsPanel, AiCodePanel, GeneratedFeaturePanel, and FeatureFilePanel, wires their callbacks, and is the single place prompts get built and Copilot gets called.

Request Lifecycle — "Start AI Code Generation"

The exact call chain from a button click to code appearing on screen, across both automation modes.

Webview

1. User clicks "Start AI Code Generation"

Control Panel's main.js posts { type: 'startAiProcessing' } with the current Playwright code / API request, chat-box text, and checked custom instruction files.

Extension Host

2. ObjectSpyPanel.handleMessage() routes the message

Reads current SettingsStore.get() (mode, language, model), fetches linked scenario, and calls runLlmRefinement().

Extension Host

3. Prompt is assembled

buildLlmPrompt() (UI mode) or buildApiLlmPrompt() (API mode) concatenates: the bundled standard (readSeniorQeInstructions() / readApiAutomationInstructions(), file-cached), any checked custom .md files (readInstructionFiles(), workspace-file-cached), a linked existing source file's retrofit section if one is linked (see "Link Existing Class file" below), the linked Gherkin scenario, and the recorded code or API request — user's free-text instructions are appended last so they win any conflict.

CopilotClient

4. sendPrompt(modelId, prompt, onChunk, token)

Resolves the model via findModel(), wraps the prompt in a single vscode.LanguageModelChatMessage.User(...), and calls model.sendRequest().

VS Code LM API

5. vscode.lm hands off to GitHub Copilot Chat

The installed Copilot Chat extension owns authentication and the actual network call — SoftPlay never sees a token or API key.

Copilot Cloud

6. The model generates and streams back

Response text arrives as an async-iterable stream (response.text), fragment by fragment.

Extension Host

7. Each fragment is forwarded live

onChunk() calls postLlmChunk(), which posts to the webview so the AI Generated Code panel updates character-by-character, not after a long silent wait.

Extension Host

8. On completion

extractCodeBlock() pulls the fenced code block out of the full response; AiCodePanel.finish() renders it; recordReceivedTokens() counts the response via the (cached) countModelTokens() and updates the Token Monitoring bar.

"Generate Feature File" and "Verify & Fix Code" follow the same shape — different prompt builder, same sendPrompt()/streaming/extractCodeBlock() plumbing.

Caching Architecture

Local system memory only — no Redis, no external cache service, no data written to disk. Everything below lives in the extension host's own process memory and disappears on window reload.

TtlCache

Environment checks

environmentCheck.ts caches checkJavaEnvironment() / checkPythonEnvironment() results. Success: 5 min TTL. Failure: 15 sec TTL, so fixing a missing JDK/package and re-clicking "Verify & Fix" doesn't hit a stale error.

TtlCache

LLM token counts

copilotClient.ts caches countModelTokens() by sha1(modelId + text). Deterministic input → deterministic output, so this is a pure win: 200-entry cap, 10 min safety-net TTL.

FileCache

Instruction / prompt files

fileCache.ts caches the bundled prompts/*.md standards and any user-linked custom .md files, validated against each file's own mtime — an edit is picked up on the very next read.

The generic cache lookup flow

Caller

1. Build a cache key

A short, deterministic string — e.g. "python:ui:<resourcesRoot>:<storageDir>" for environment checks, or "<modelId>:<sha1 of prompt text>" for token counts.

TtlCache.get()

2. Look it up

Expired entries are deleted lazily on read (no background timers running). A hit returns immediately — zero process spawns, zero LLM round-trips.

Miss path

3. Compute for real

Run the actual execFile probe or the actual model.countTokens() call.

TtlCache.set()

4. Store and bound

Written with its TTL. If the cache is already at its size cap, the oldest-inserted entry is evicted first (simple FIFO, not full LRU) — memory can never grow unbounded across a long editing session.

LLM Integration Details

SoftPlay never talks to an LLM provider directly. It exclusively uses VS Code's built-in Language Model API, which in turn is served by whichever GitHub Copilot Chat models the user's own subscription exposes.

Discovery

vscode.lm.selectChatModels({ vendor: 'copilot' })

Called by listCopilotModels() to populate the Model dropdown in Settings, and by findModel() every time a request needs to resolve an id to a live LanguageModelChat handle. Never hardcodes a model list — whatever Copilot exposes today is what shows up.

Generation

LanguageModelChat.sendRequest(messages, options, token)

Called by sendPrompt() with a single LanguageModelChatMessage.User(prompt). Returns a response whose .text is an async-iterable stream, consumed with for await and forwarded chunk-by-chunk to the UI.

Token accounting

LanguageModelChat.countTokens(text, token)

Called by countModelTokens() (cached — see above) to power the Token Monitoring bar, using the model's own real tokenizer rather than a character-count guess, plus model.maxInputTokens for the context-window ceiling.

Failure handling

CopilotUnavailableError

Thrown when no model resolves (Copilot Chat not installed, not signed in, or no models exposed) — surfaced as a clear status message rather than a raw stack trace anywhere the AI features are triggered.

🔐 VS Code shows its own one-time consent dialog the first time any extension calls the Language Model API in a session — SoftPlay does not, and cannot, bypass that gate.
🦜🔗 New — built with LangChain

Verify & Fix Agent

"Verify & Fix Code" no longer runs a hardcoded loop — it runs a small, bounded LangChain tool-calling agent that tests its own work and decides for itself what to do next.

Executive summary

The AI now tests its own work instead of guessing blind

Before: SoftPlay ran the code once, and on failure, sent the error to Copilot for a single guess at a fix — repeated up to 5 times, hoping each guess was better than the last. Now: a real autonomous agent, built on LangChain (the industry-standard framework for tool-using AI agents), is handed three tools — run the code, read a file, read the linked test scenario — and it decides for itself, turn by turn, whether it has enough information, whether to look something up first, and when its fix is actually correct. It never just claims success: the loop only stops when the code has genuinely, verifiably run without error.

🏃 Tool 1

run_code

Compiles/runs the agent's current candidate for real, in the same disposable scratch project as before. A human must approve every single execution — no exceptions, exactly like the feature this replaces.

📄 Tool 2

read_file

Lets the agent inspect a file inside its own scratch project (a build file, an earlier run's output). Every path is checked to stay inside that one folder — it can never reach anywhere else on the machine.

🥒 Tool 3

read_feature_file

Read-only access to whichever Cucumber .feature file the user already linked via "Link Feature file" — the scenario the fixed code needs to satisfy.

Where LangChain fits, precisely

@langchain/core — BaseChatModel

VSCodeCopilotToolCallingModel

A custom adapter class extending LangChain's BaseChatModel, wrapping the exact same vscode.LanguageModelChat handle every other Copilot call in this extension uses. LangChain never talks to a model directly here — it talks through this adapter, which translates to/from vscode.lm's own native tool-calling API (LanguageModelChatTool, LanguageModelToolCallPart). No second credential, no different provider — same Copilot subscription, same consent dialog.

@langchain/core — tools & messages

tool() + Zod schemas, AIMessage/ToolMessage

Each of the three tools above is a real LangChain StructuredTool, its input validated by a Zod schema before it ever runs. The conversation itself is built from LangChain's own message types (SystemMessage, HumanMessage, AIMessage, ToolMessage) — the same primitives used across the entire LangChain ecosystem.

Deliberately NOT used

LangChain's AgentExecutor

The turn-by-turn loop is hand-written (runToolCallingAgent()) directly over LangChain's core primitives rather than LangChain's own general-purpose agent executor — a regulated environment needs an auditable, fully explicit stopping condition (a tool-verified pass, never the model's self-assessment), which a hand-rolled loop guarantees far more transparently than a general-purpose black box.

Deliberately NOT used

LangSmith tracing

LangChain's tracing/telemetry SDK ships as a dependency of @langchain/core but is opt-in only (activated by an environment variable this extension never sets). An automated test actively proves zero outbound network calls happen during an agent run — see Quality & Testing below — rather than only documenting the claim.

Enterprise safeguards

🛟 Automatic fallback

If the agent path fails for any reason unrelated to the code itself (e.g. Copilot temporarily unavailable), SoftPlay automatically falls back to the exact, original, previously-shipped fix loop — kept in the codebase verbatim as runLegacyVerifyFixLoop() — so this rewrite can never leave "Verify & Fix Code" more broken than before it existed.

🔒 Sandboxed file access

read_file's path is checked against the scratch directory on every call (resolveWithinScratchDir()) — an absolute path, a .. traversal, or a sibling-directory trick are all rejected. Directly unit tested against ten adversarial path shapes.

⏱️ Bounded, always

A hard cap on real executions (5, same as before) AND a separate hard cap on total agent turns (17) — a pathological loop that only ever inspects files without acting can never run away in cost or latency.

🙋 Human-in-the-loop, unchanged

The confirmation modal before every single code execution — the one safeguard this whole feature is built around — lives inside the run_code tool itself, so it holds no matter how many turns the agent takes internally.

Quality & testing

The agent's entire decision-making core (agent/verifyFixAgent.ts) has zero dependency on vscode by design, specifically so it can be driven by a scripted fake model in a plain, fast, offline unit test suite — no Extension Development Host, no real Copilot subscription, no network access required to run it.

20/20 passing

Node's built-in test runner (node --test) — zero new test-framework dependency.

Every stop condition

Success, decline, max-steps, no-further-action, cancellation, and hard model errors — each has its own test.

Security path tested

10 adversarial path-traversal shapes against read_file's sandbox, individually asserted.

Reusable Components (RAG)

Code generation now retrieves your team's own tested helpers — a database connection, an auth pattern, whatever you've already built — instead of asking Copilot to reinvent them from scratch every time.

Executive summary

The AI reuses your team's real code instead of guessing at it

A team drops its existing helper classes into a one-time "Generate RAG Corpus format" step (Settings). From then on, every "Start AI Code Generation" — UI or API mode — searches that library locally (no network call, no external vector database, no FAISS) for anything relevant to the current scenario, and if it finds a match, hands Copilot the exact code and import statement to call instead of writing new logic. A scenario like "Login to Postgres database, query a specific table, validate the result" now reuses your team's own PostgresHelper rather than Copilot inventing its own JDBC boilerplate — less hallucination, more consistency across everyone using this extension.

RAG core — fully local, zero external services

Schema

ragTypes.ts

The recipe schema — Zod-validated frontmatter (id, title, tags, automationMode, language, imports) every .github/rag/*.md file must satisfy. Matching text also folds in each recipe's own folder, subfolder, and filename (relative to .github/rag/) — a helper filed under database/cassandra/connection-helper.md is findable by "cassandra" alone, even if that word appears nowhere in its title, tags, or body.

Parsing

ragFrontmatter.ts

Parses and serializes .github/rag/*.md recipe files — the same YAML-frontmatter-plus-Markdown-body shape as this page's own component library.

@langchain/core — Embeddings

tfidfEmbeddings.ts

A zero-dependency Embeddings implementation — TF-IDF over unigrams AND bigrams, with light plural stemming and a hand-curated synonym table for test-automation/DB/API vocabulary (e.g. "db" ↔ "database"), L2-normalized. No model download, no WASM runtime, no network call, ever.

@langchain/core — VectorStore

flatVectorStore.ts

Brute-force cosine-similarity search — the "no FAISS, no vector DB" answer. At a curated library's realistic size (dozens to a few hundred recipes), an exact linear scan is sub-millisecond and genuinely simpler than an approximate-nearest-neighbor index.

Indexing

ragIndexBuilder.ts / ragIndexer.ts

Pure builder plus vscode-glue with mtime-based caching — the exact same "re-read only when something actually changed" pattern as cache/fileCache.ts.

Retrieval

ragRetriever.ts

Runs the search and formats the prompt section. Target language is a hard filter — a Python-only helper never shows up while generating Java, since the resulting code would be genuinely unusable. Automation mode is deliberately a soft preference, not a filter — a recipe tagged for the "wrong" mode (a per-file guess made in isolation when it was generated) can still surface for a strongly-relevant match instead of being silently excluded outright.

☝️ Automatic by default, exact when you choose: with nothing checked in the "RAG Data" list, retrieval runs automatically on every generation and whatever it finds (or doesn't) is already baked into the prompt the Token Monitoring bar measures before you click Generate — a matched helper's tokens are already counted; if nothing matched, it added zero. Recipes you check are a different path: they skip retrieval, ranking and size packing entirely and hold the same top priority as checked Custom Instructions — each is sent in full under a "HIGHEST PRIORITY" header with a recency reminder, outranking the built-in standard, example code and chat text. When a checked recipe and a checked Custom Instructions file genuinely conflict, neither simply wins: the more specific rule is followed and both are named in a comment in the output. A checked recipe that is missing, invalid or not tagged for the selected language — or a selection too large for the model — stops the request before anything is sent, and is never silently dropped, trimmed or retried without. (Agentic Mode has no RAG Data checkboxes, so it is unaffected.)

"Generate RAG Corpus format" — the one-stop onboarding step

Settings — new segment

Drop files in, recipes come out

A drag-and-drop zone (plus a native file picker) in Settings accepts a broad range of source/config files. Each file's content is read client-side and sent to ragCorpusGenerator.ts, which asks Copilot to convert it into a properly-structured recipe via generate-rag-recipe.md — analyzing arbitrary code to infer a title, tags, target language, and the exact import statement is a genuine LLM judgment call, not something a template could do.

Never a silent failure

Malformed output still becomes a usable file

ragRecipeNormalizer.ts validates every model response; if it doesn't parse, it falls back to a filename-derived, schema-valid wrapper around the model's raw output and flags it for manual review — a generation request always produces something, never a silently dropped file. Batch overwrite confirmation and a live per-file progress log round out the flow; .github/rag/ is created automatically if it doesn't exist yet.

⚠️ The generation prompt explicitly forbids reproducing a real secret from an uploaded file — these recipes are git-tracked and resent to Copilot on every future generation, so a real password/key must never end up inside one.

Data Flow & Security Boundary

What stays on the developer's machine, and the one thing that ever leaves it.

🖥️ Stays on the local machine

  • Recorded Playwright code (Codegen writes to a temp file, polled and streamed locally)
  • Every child process: Chrome/Edge, pytest, mvn, java, python
  • All three caches (environment checks, token counts, instruction files)
  • Settings (context.globalState) and saved test files
  • Environment probing (java/mvn/python version + package checks)
  • Every real password/token/API key value — Auto Password Encryption turns it into an ENC[...] token before anything is built or sent (see Components)
➜ Only the assembled prompt text (and the model's reply) crosses this line

☁️ Sent to GitHub Copilot's cloud

  • The full prompt: recorded/API code, bundled + custom instructions, linked scenario, and chat-box text
  • Any credential-shaped value in that prompt is already an encrypted ENC[...] token, never the real value
  • Governed entirely by the user's own GitHub Copilot subscription and GitHub's data-handling policy
  • Only when "Link with GitHub Copilot LLM" is switched on — off by default
⚠️ Auto Password Encryption catches credential-shaped fields automatically, but it's a heuristic, not a guarantee — avoid pasting real production data (customer PII, production passwords) into recorded flows or the API request builder as a matter of policy, non-credential fields included.

Component Reference

One row per module — its job, and what it never does.

Feature — Auto Password Encryption

Every credential, encrypted by default — UI Automation and API Automation alike

Any password typed into a recorded browser flow, or entered into any of the API Automation Authorization tab's auth types (API Key, Bearer, Basic, Digest, OAuth 1.0/2.0, Hawk, AWS Signature, NTLM, Akamai EdgeGrid), is encrypted locally the instant SoftPlay touches it — before it is ever included in a Copilot prompt, and before it is written into the saved AI Generated Code file. There is no setting to turn this off: it is the standard behavior for both automation modes. A matching decrypt call — plus, for Python, a small bundled pure-Python AES implementation, so no pip install is ever required — is added to the generated file automatically, so the test still actually runs.

Algorithm

AES-256-CTR + HMAC-SHA256, Encrypt-then-MAC, with independently derived cipher/MAC keys. Natively available in Node, the JDK, and (via a bundled implementation) Python — zero extra dependencies to install offline.

Key storage

One 32-byte key per install, generated once and held in VS Code's own SecretStorage — OS-keychain-backed (Windows Credential Manager / macOS Keychain / libsecret) — never a hardcoded key, never a plain file.

Token format

ENC[v1:iv:tag:ciphertext] — self-describing and base64, safe to embed directly as a Java or Python string literal with no escaping.

Runtime key delivery

SoftPlay_SECRET_KEY environment variable — set automatically for "Verify & Fix Code"; a real CI/CD pipeline supplies it from its own secrets manager (Vault, CyberArk, Azure Key Vault, ...) instead.

Feature — Link Existing Class file

Retrofit new automation into a file you already have, instead of generating a new one

Available in both UI Automation and API Automation, for both Java and Python. Click Link Existing Class file (Generated Code section, right below "Start AI Code Generation") and pick a single .java or .py file — from inside the workspace or anywhere else on disk. A compact status chip shows the file name and detected language, with the full path in its tooltip, plus a small ✕ to unlink; clicking the button again lets you replace the linked file at any time, and cancelling the picker leaves whatever is currently linked untouched. If the file's language doesn't match the language currently selected in Settings, SoftPlay asks you to either switch Settings to match or pick a different file — it never switches the language silently.

The next click of Start AI Code Generation (or Regenerate AI Code) reads the file fresh, asks the model to analyze it first, and produce the complete, integrated version of that same file — reusing its existing methods, fields, imports, and setup/teardown wherever they genuinely fit, adding only what the new request needs, and never appending an unrelated class underneath it. The result appears in the usual AI Generated Code panel for review; nothing is ever written back to the linked file automatically — an explicit Save Code click is still required, exactly as for any other generated result.

A newly recorded or requested flow often independently redoes steps an existing method already performs (navigating to the same page, dismissing the same consent dialog, logging in) simply because that's how the action was captured — this is not a signal that a new method needs its own copy of those steps. The retrofit prompt explicitly compares a new method's required steps against the step-level body of every existing method (not just names or signatures) and, when they overlap, asks the model to extract the shared portion into one reusable helper called by both the existing and the new method, rather than duplicating it inline. This is a strengthened instruction, not a mechanical guarantee — prompting alone cannot promise perfect deduplication of every possible step sequence, so review generated code before saving it, same as always.

Quick Troubleshooting

The handful of messages people actually run into.

"No Copilot chat models found"

Install the GitHub Copilot Chat extension and make sure you're signed in to a GitHub account with Copilot access.

Environment check failed (Java/Python)

Install the missing tool and make sure it's on your system PATH, then click Verify & Fix again — the failure is only cached for 15 seconds.

Nothing happens when I click Start

Check the "SoftPlay" Output channel (View → Output, then pick SoftPlay from the dropdown) for the exact error.

My generated code seems out of date

Click "Regenerate AI Code" — it always resends your current, live code, not an old snapshot.
