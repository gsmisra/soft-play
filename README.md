# softPlay

A VS Code extension for QA/testing teams that drives a real, visible Chrome
window (via CDP — never a VS Code webview iframe), lets you spy on page
elements to generate short **relative** Playwright locators (XPath/CSS) with
live uniqueness scoring, and records your actions into enterprise-grade
Playwright automation code (Java or Python).

This repo is being built in phases; see the project's "Master Build Prompt"
doc for the full spec. **Current state — Phase 5 (feature-complete per the
spec's roadmap) plus two follow-up passes:** extension scaffold,
Start/Stop/Navigate over CDP, Object Spy (hover-to-highlight, a
priority-tiered relative locator engine that keeps refining — primary
candidate → sibling-axis → a guaranteed-unique positional fallback — until
it reaches uniqueness, with live DOM-verified counts including inside open
shadow roots and iframes, a deduplicated Elements table with iframe/shadow
badges and multi-select delete), a Settings panel (locator type, code-gen
language/version, GitHub Copilot linking) persisted via
`context.globalState`, Generate Code (records real browser actions into a
Page-Object-style Playwright class in Java or Python, editable and
syntax-highlighted right in the panel, with value/state assertions and a
submit-aware settle wait), and AI Assist — an optional second, independently
editable/scrollable code view generated by a GitHub Copilot chat model from
the same captured locators, asked to match the Playwright view's style.

## Using Object Spy

1. **Start**, then **Navigate** to a page.
2. Click **Object Spy: Off** to turn it on (it turns red — "Object Spy: On").
   Hover any element in the real Chrome window: a red box tracks it live.
3. Click an element to capture it. The click is intercepted (no navigation/
   form submit happens) and a row appears in the Elements table.
4. Click **Object Spy: On** again to turn it off.

The locator type (CSS or XPath, default **XPath**) is controlled from the
**Settings** panel — click the ⚙ button, or run **"softPlay: Open Settings"**
from the command palette.

### Locator uniqueness — the top priority

Every candidate's match count comes from actually querying the live DOM
(`querySelectorAll`/`document.evaluate`), never a heuristic guess, and
computing a locator never settles for "good enough": it keeps trying until
it reaches an actually-unique locator.

1. **Primary tiered candidate** — stable test attributes
   (`data-testid`/`data-test`/`data-qa`/`data-cy`) and non-generated `id`s
   ("Excellent") → `aria-label`/`role` ("Good") → name/placeholder or a
   selector scoped to a nearby stable ancestor ("Fair") → text/attribute
   XPath ("Weak").
2. **Sibling-axis refinement**, if that's still ambiguous — XPath's
   `following-sibling::`/`preceding-sibling::` axes, or CSS's `+`/`~`
   combinators, anchored on a nearby sibling that itself has a stable
   attribute or id (see [BrowserStack's following-sibling guide](https://www.browserstack.com/guide/following-sibling-xpath-in-selenium)
   and [XPath axes reference](https://www.scientecheasy.com/2019/08/xpath-axes.html/)).
   CSS combinators only look forward in document order, so this tier is
   XPath-only when the nearest stable anchor comes *before* the target in
   markup.
3. **Guaranteed-unique positional fallback**, as an absolute last resort —
   a positional XPath predicate, `(relativeXPath)[n]`, verified against the
   live DOM to actually resolve to exactly one element. Still relative,
   never an absolute `/html/body/...` path. This is the only tier that can
   report a `locatorType` of `xpath` even when Settings is set to CSS,
   since only XPath's positional predicate is natively verifiable —
   Playwright's own `locator()` auto-detects XPath regardless, so generated
   code still works correctly.

"Ambiguous (N)" only ever appears transiently while refining; by the time a
row lands in the table, its locator has already been driven to uniqueness
(or the page has fewer than one matching element, in which case it reads
"Not found").

## Elements table

Every element Object Spy captures — and every element Generate Code records
an action on — lands in one deduplicated table (re-scanning the same
element, same locator, never adds a second row):

| Column | Contents |
| --- | --- |
| *(checkbox)* | Select rows for **Delete Selected**, or use the header checkbox to select all |
| Element Name | A short **camelCase** name auto-generated from the element's visible text, or a stable attribute (test id/name/placeholder/aria-label), or its tag, in that order — e.g. `loginButton`, `username`, `div3`. Carries an **iframe** and/or **shadow** badge when the element was found inside one. |
| Element Locator | The generated CSS or XPath string |
| Locator Quality | Excellent / Good / Fair / Weak — the tier the final locator came from |
| Locator Uniqueness | Unique / Ambiguous (N) / Not found |

Select exactly one row and click **Highlight On Page** to bring the real
Chrome tab to the front and flash a rapidly-blinking red box around that
element for 5 seconds — useful for confirming which row is which,
especially after the table's grown long. If you've navigated away from the
page the element was captured on, you'll get a warning instead (it can only
highlight what's actually on the current page).

Three actions sit below the table:
- **Delete Selected** — removes the checked rows.
- **Save Locators (JSON)** / **Save Locators (.properties)** — prompts for a
  destination folder and a file name, then writes a simple `elementName ->
  locator` mapping (a JSON object for JSON; `elementName=locator` lines for
  `.properties`) — duplicate names are disambiguated with a numeric suffix.

## Using Generate Code

1. Click **Generate Code** (auto-enables Object Spy if it wasn't already on).
2. Use the real Chrome window normally: click things, type into fields, pick
   from `<select>`s, check boxes, press Enter/Tab/Escape. Unlike plain Object
   Spy, these clicks are **not** intercepted — the real app still navigates,
   submits, etc. — while each action is captured in the background and turned
   into a Playwright step in the **Generated Code** panel.
3. If an action's locator matches more than one element, recording **pauses**
   and an amber banner prompts you to fix the locator (pre-filled, editable)
   or **Skip** the action — it never silently guesses an `.nth()` index. Fix
   the text and click **Resume** to re-verify against the live DOM and
   continue. Pausing only suppresses reporting *new* actions — clicks keep
   working normally the whole time (including ones that navigate), since
   the real app still needs to behave exactly like it would with no
   extension attached at all while you sort out the ambiguous one.
4. Click **Stop Code Generation** to pause without losing what's been
   generated — click **Generate Code** again to resume the same session.

The very first navigation the browser was already on when you clicked
**Generate Code** — wherever it got there, including a URL you typed
directly into the real Chrome window's own address bar (not just the
Navigate button or manual browsing before recording started) — is captured
as the flow's opening `page.navigate(url)`/`page.goto(url)` step, so the
generated test is actually runnable on its own instead of starting on a
blank page. Any later top-level navigation is captured the same way, as its
own step that breaks the fluent chain, whether it came from the extension's
Navigate button or was typed straight into the browser's address bar; a
navigation that happens as the *side effect* of a recorded click (e.g.
clicking "Sign In") doesn't get a separate step — Playwright's own
auto-waiting on that click already covers it. (Address-bar navigations are
detected via a short quiet window after the page's `load` event — if no
click/fill/etc. was reported in the ~2 seconds before the page loaded, the
new URL is treated as a direct navigation rather than the side effect of
something already being recorded.)

**New tabs and windows are followed automatically.** If a recorded click (or
raw Object Spy) opens a new tab or window — e.g. a "Sign in" link on a page
like Gmail that opens `accounts.google.com` in its own tab — the extension
installs the same capture/recording agent on that new page the instant
Chrome creates it, so Object Spy and Generate Code keep working there with
no extra steps. Every tab and window opened during the session (not just
the first one) is tracked this way for as long as the browser stays
attached.

Every time a new action is actually recorded, a **"New code recorded."**
label blinks green next to the Playwright Code header for a couple of
seconds to draw your eye to it.

The **Playwright Code** panel is a real, editable, syntax-highlighted code
editor — not read-only text. Edit it directly (keyword/string/comment/
annotation/method/class-name highlighting, styled close to VS Code's Dark+
theme); once you've made a manual edit, a newly recorded action won't
silently overwrite it — a small banner offers **Refresh** if you want the
freshly generated version instead. Click **Save Code** to write the current
editor contents to a file — the save dialog defaults to a filename derived
from the class name below, with a `.java` or `.py` extension depending on
the language selected in Settings (you can rename it, same as any save
dialog). Click **Copy Code** to copy the current editor contents to the
clipboard instead — the button flashes "Copied!" for confirmation (falling
back to a hidden-textarea copy if the browser Clipboard API is unavailable
in the webview). The same two buttons are also on the **AI Generated Code**
panel, for whatever GitHub Copilot produced.

**Output structure is Page-Object-ready, not a flat script:** the page
object and test class are named after the **title of the last page you
navigated to** — e.g. navigating to a page titled "Apple" produces
`ApplePage`/`AppleTest` (Java) or `ApplePage`/`test_apple_flow` (Python)
instead of a generic `GeneratedPage`/`GeneratedTest`. This tracks the title
regardless of *how* you navigated — the Navigate button, clicking a link,
submitting a form, or a client-side route change in the real Chrome
window — not just navigations made through the extension's own UI. The page object class
exposes one fluent method per unique (action type, locator) pair — typing
into the same field twice reuses one `fillUsername(value)` method rather
than duplicating it — and the test class composes them in the order they
were recorded. Wait/assertion strategy:
Playwright's own action methods already auto-wait for actionability, so no
arbitrary sleeps are ever emitted; on top of that, every `fill`/`selectOption`
step asserts the field actually reflects the value afterward, every
`check`/`uncheck` asserts the resulting state, and a click identified as
submit-like (an `<a>`, a submit button, or `input[type=submit|button]`) is
followed by a load-state wait so the next step doesn't race a page that's
still navigating.

**Locators are never hardcoded inline** — every unique locator gets one
named constant in a generated `Locators` class (Java `static final String`
fields; a Python `class Locators` with class attributes), using **the exact
same value as the Element Name column** in the Locator Output table — no
case transformation, so `username`/`logIn` in the table is `username`/`logIn`
in the code too, never `USERNAME`/`LOG_IN` (a deliberate departure from the
usual Java/Python constant-naming convention, so one name identifies a
locator everywhere: the table, the exported JSON/.properties file, and the
generated code). Page Object methods reference `Locators.username` rather
than embedding `"[data-testid=\"username\"]"` directly, so a locator only
ever needs updating in one place. An element interacted with more than one
way (e.g. a checkbox that's both clicked and checked) shares a single
constant rather than duplicating the locator string per action.

Language and framework: Java emits a JUnit 5 test class (`assertThat` from
`PlaywrightAssertions`); Python emits a pytest test function (`expect` from
`playwright.sync_api`). Both idiomatically follow the Language/runtime
version picked in Settings — Java 17+ uses `var` for each method's local
`Locator` (never for a field: `var` is only legal for a local variable with
an inline initializer, so `GeneratedTest`'s fields stay explicitly typed
regardless of version), Python uses a typed `Page` parameter and `-> "GeneratedPage"`
return type. The generator is an in-house template layer — it does not
depend on any of Playwright's internal/unexported recorder classes, which
aren't public API and would break across Playwright versions.

## Kill All Browsers

The toolbar's **Kill All Browsers** button (click twice to confirm — VS
Code webviews don't reliably support native `confirm()` dialogs, so it arms
on the first click and confirms on the second, within 3 seconds) closes any
Chrome process this extension itself launched and clears every captured
locator and all generated code. It intentionally does **not** scan the OS
for other `chrome.exe` processes to kill — that could just as easily kill
your everyday browsing Chrome, an unacceptable side effect for a "clear my
automation session" button. If you attached to an already-running Chrome
instead of launching one, that Chrome is left running, same as a plain Stop.

## AI Assist (GitHub Copilot)

Requires the **GitHub Copilot Chat** extension installed and signed in.
softPlay never bundles or hardcodes a model list — it asks VS Code's
Language Model API (`vscode.lm.selectChatModels`) what's actually available
at the moment you enable this, so whatever models your Copilot
subscription/extension version exposes are what show up.

1. Open **Settings**, turn on **Link with GitHub Copilot LLM**, and pick a
   model from the dropdown (populated live from Copilot — "No Copilot chat
   models found" means Copilot Chat isn't installed or you're not signed
   in). This reveals a collapsible **AI Assist** section and a second
   **AI Generated Code** view in the main panel.
2. Expand **AI Assist**. It auto-detects every `.github/**/*.md` file in
   your workspace (instructions, skills, custom prompts) — check whichever
   ones you want followed, or none. Click **Refresh file list** if you add
   files after opening the panel.
3. Click **Send to Copilot**. This sends the model a single message
   containing: the content of your selected `.md` files, the JSON of every
   captured locator, and the current **Generated Code** view's content as a
   style reference — explicitly asked to reproduce the same Page-Object
   structure, reuse the given locators as-is, and return only a fenced code
   block. The response streams into the **AI Generated Code** view live as
   it arrives.
4. Both code views are independently editable, syntax-highlighted, and
   independently scrollable (side by side when the panel is wide enough —
   drag the Activity Bar view wider, or drag it into the editor area, to see
   both at once; they stack on a narrow sidebar). **Save Code** on either
   view works the same way as the Playwright view's.

**Consent:** the first time any extension calls the Language Model API in a
session, VS Code shows a one-time permission dialog — that's Copilot's own
gate, not something softPlay controls. Per the API's own contract, this
call only ever happens in direct response to your **Send to Copilot**
click, never automatically.

**Honest limitations, since this integration depends on an environment this
build couldn't exercise end-to-end the way the rest of the extension was
(against a real, locally installed Chrome browser):**
- The Language Model API has no distinct "system" role — instructions,
  locators, and the style reference are all folded into one user message.
  Model behavior/quality depends entirely on the Copilot model chosen.
- Models sometimes add commentary despite being told not to; softPlay
  extracts the first fenced code block from the response as a best-effort
  cleanup, falling back to the raw response if there's no fence.
- "Side by side" is responsive, not a fixed split — a narrow Activity Bar
  sidebar stacks the two views vertically instead, since a literal
  side-by-side layout wouldn't be usable at typical sidebar widths.

## Edge cases: shadow DOM, iframes, dynamic ids

- **Shadow DOM:** hover/click targeting uses `composedPath()[0]` rather than
  `e.target`, so an element inside an **open** shadow root resolves correctly
  instead of retargeting to the shadow host. Live uniqueness counting for CSS
  locators pierces every open shadow root it finds, so a `[data-testid="x"]`
  inside a shadow root is correctly reported unique instead of "0 matches".
  XPath's own `document.evaluate()` cannot pierce shadow DOM at all — that
  mirrors Playwright's own XPath engine, so prefer CSS locators in
  shadow-heavy apps. Closed shadow roots are inherently inaccessible to any
  script, Playwright included.
- **iframes:** Object Spy and Generate Code both work inside same-origin
  *and cross-origin* iframes — the CDP-based architecture (§ above) reaches
  every frame regardless of the DOM's same-origin policy, which matters for
  real banking pages that commonly embed cross-origin iframes (payment
  widgets, SSO/2FA). **Known limitation:** a locator captured inside an
  iframe is still generated as a bare `page.locator(...)`, not wrapped in
  `page.frameLocator(iframeSelector).locator(...)` — actions don't yet carry
  which frame they came from, so a recorded flow touching an iframe's
  contents needs that wrapping added by hand.
- **Dynamic/generated ids:** filtered out of the "id" locator tier alongside
  GUIDs and long hashes — covers React 18's `useId()` shape (`:r0:`), MUI,
  Radix, Chakra, Headless UI, Reach UI, Angular Material/CDK, and Ember's
  autogenerated id patterns.

## Why CDP-attach, not a webview iframe

Most real sites — virtually all banking sites — send
`X-Frame-Options`/`Content-Security-Policy: frame-ancestors` headers that
block iframing entirely. Instead, this extension either attaches to an
already-running, debug-enabled Chrome or Edge, or launches a new process
with `--remote-debugging-port`, then drives it with `playwright-core`'s CDP
connector. Once attached, everything works identically to a browser
Playwright launched itself — and since `playwright-core` (unlike the full
`playwright` package) never bundles or downloads a browser binary of its
own, nothing is ever fetched over the network to make this work; see
"Browser choice" below.

## Browser choice — Chrome or Edge only, nothing ever downloaded

softPlay drives **Google Chrome or Microsoft Edge only** — pick which one in
Settings (default Chrome). There is no third option, and there never will be
a step that downloads a browser binary:

- The extension depends on **`playwright-core`**, not the full `playwright`
  npm package — `playwright-core` is the API-only build and has no
  postinstall step that fetches a browser; `npm install` here never
  downloads anything browser-related, in this network or any other.
- `src/browser/chromeFinder.ts` only ever probes for an
  existing **Chrome or Edge** install at well-known OS paths (on Linux,
  deliberately `google-chrome-stable`/`microsoft-edge-stable` only — never
  the open-source `chromium-browser` package). If neither is found, Start
  fails with a clear error asking you to set
  `objectSpy.chromeExecutablePath` — it never tries to install one.
- Generated Playwright code follows the same rule: the Java template passes
  `.setChannel("chrome")`/`.setChannel("msedge")` (matching your Settings
  choice) to Playwright's launcher, which makes it drive your machine's real
  installed browser instead of downloading Playwright's own bundled one; the
  Python template's header comment tells you to run
  `pytest --browser-channel=chrome` (or `msedge`) for the same reason.

## Security note (read this in a bank environment)

The Chrome DevTools Protocol debug port (default **9222**) is bound to
`127.0.0.1` only. **Anything with access to this port has full control of the
browser session** — including any site content, cookies, and (if you enable
"Use Real Chrome Profile") your real logins. Do not change the bind address,
and be mindful of what else runs on the same machine while the port is open.

npm install

## Building a .vsix

```bash
build-extension.bat
```

Installs dependencies, bumps the patch/build number in `package.json`
(`scripts/bump-version.js`), compiles, and packages a single `.vsix` —
deleting any previous one first, so exactly one is left in the folder
afterward. That same version number is what shows as the **v0.1.x** badge
on the main panel. Run it any time you want an installable build; every run
advances the build number, so re-running without other changes is enough to
produce a new, distinguishable package. Install the result via VS Code's
**Extensions: Install from VSIX...** command.

## Using it

softPlay's main UI lives in the **Activity Bar** — the vertical icon rail on
the far left/right edge of the VS Code window (same place as Explorer,
Search, Extensions) — not a floating editor tab, so it's always one click
away. Look for the softPlay icon (a play triangle inside a target ring) and
click it to open the sidebar panel.

> **Just installed and don't see the icon?** Reload the window
> (**Developer: Reload Window** in the Command Palette, or just close and
> reopen VS Code) — a newly installed/updated extension's Activity Bar
> contribution doesn't always appear until the window reloads. If it's
> still missing, right-click anywhere on the Activity Bar and make sure
> "softPlay" is checked in that context menu (icons can be hidden this way).
> You can also always reach it via the Command Palette regardless: run
> **"softPlay: Open Panel"**.

1. Open the softPlay sidebar view, then click **Start**. The extension
   either attaches to a Chrome already running with the configured debug
   port, or launches a new Chrome window itself.
2. Enter a URL in the address bar and click **Navigate** (or press Enter).
3. Click **Stop** to disconnect. If the extension launched Chrome itself,
   that process is terminated; if it attached to a Chrome you already had
   running, it is left running untouched.

## Layout: three collapsible sections

The panel is organized into three independently expandable/collapsible
sections (native, click the header to toggle — no separate button needed):

- **Control Panel** — Start/Stop/Navigate, Object Spy, Generate Code/Stop,
  Settings, Kill All Browsers, and the ambiguous-locator resolution banner.
- **Locator Output** — the Elements table and its actions (Highlight On
  Page, Delete Selected, Save Locators).
- **Generated Code** — AI Assist (when enabled) and the code editor(s).
  Collapse the other two sections to give this one the most room; the code
  editor itself is sized to a large share of the panel's height (`68vh`) so
  it reads like a real, spacious code view rather than a cramped text box.

Diagnostic/informational messages (Chrome launch progress, each recorded
action, disconnects) go to a dedicated **softPlay** Output channel —
**View → Output**, then pick "softPlay" from the dropdown — rather than a
panel inside the sidebar, freeing that space up for the table and code
editor. Actual errors (failed to launch Chrome, failed to navigate) still
show as VS Code notifications, same as before.

## VS Code Settings

| Setting | Default | Notes |
| --- | --- | --- |
| `objectSpy.cdpPort` | `9222` | Localhost-only CDP debug port. |
| `objectSpy.chromeExecutablePath` | *(auto-detect)* | Override if Chrome/Edge isn't found automatically. |
| `objectSpy.useRealChromeProfile` | `false` | See caveat below. |
| `objectSpy.userDataDir` | *(auto)* | Explicit `--user-data-dir` override. |
| `objectSpy.startUrl` | `about:blank` | Opened on Start. |

Locator type, language, and language version are **not** VS Code workspace
settings — they live in the in-panel **Settings** panel (`context.globalState`),
covered below.

**Caveat on `useRealChromeProfile`:** recent Chrome releases block enabling
remote debugging against the browser's *live* default profile directory, as a
session-hijack mitigation. If Start succeeds but never attaches, this is the
most likely cause — the workaround is a dedicated copy of the profile
directory rather than the one Chrome is actively using day-to-day. This
should be re-verified against whatever Chrome version is installed on the
target machine; it's flagged here rather than silently assumed to work.
